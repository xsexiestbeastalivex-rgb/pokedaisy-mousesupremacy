# Development and integration

## Development environments

The published Codex Cloud configuration described in the brief has Gradle 8.10.2, Temurin 21 and a prewarmed Compose Desktop build. Use that environment for companion UI when available. The selected Linux Work checkout is a separate environment. Its verified or blocked runs are in [project status](PROJECT_STATUS.md). Use Android SDK or GitHub Actions for native APK compilation. Use a physical WSA session for the target pointer proof.

Follow [upstream build notes](../DEVELOPMENT.md#build) and [testing instructions](../../CLAUDE.md#testing-quick-by-default-full-runs-only-with-the-users-ok). The workflow in [upstream CI](../../.github/workflows/ci.yml) uses JDK 17, the Gradle 8.10.2 wrapper, SDK platform 34, NDK `28.2.13676358`, CMake `3.22.1` and pinned recursive submodules. For its default app configuration, omit optional Azahar and keep the required pinned mGBA, rcheevos, melonDS, DSperate and BananaDS dependency paths. The initial WSA build uses `-Ppokedaisy.x86_64=true`. Android API 26 is the app minimum.

```bash
git -c submodule.third_party/azahar.update=none submodule update --init --recursive
sdkmanager --install 'platforms;android-34' 'build-tools;34.0.0' 'ndk;28.2.13676358' 'cmake;3.22.1'
./gradlew :app:assembleDev -Ppokedaisy.x86_64=true
./gradlew :app:testDebugUnitTest -Pquick --tests '*BattleInputControllerTest'
./gradlew :shared:testDebugUnitTest -Pquick --tests '*BattleCursorTest'
```

## Exact-commit development APKs

Use the [recorded baseline artifact](PROJECT_STATUS.md) for documentation or pure-logic work when it can answer the check. Record the artifact's SHA separately from the working branch SHA. For a change that needs to run on a device, get a build of the exact reviewed source commit.

The [fork artifact workflow](../../.github/workflows/mousesupremacy-dev-apk.yml) has a narrow internal PR trigger for edits to its own YAML. Ordinary PRs run inherited CI, whose `assembleDebug` job serves a different purpose. Keep this on-demand artifact job outside universally required checks. Before the workflow reaches the fork default branch, use the existing artifact if applicable or build `app/build/outputs/apk/dev/app-dev.apk` from an isolated checkout at the required commit using the pinned steps above.

After the workflow reaches the default branch, dispatch **MouseSupremacy development APK** in Actions using a same-fork branch already pinned to the intended full SHA. Verify its remote head with `git ls-remote --exit-code origin "refs/heads/$build_ref"` (with `$build_ref` set to that branch and `origin` verified as this fork) and keep the branch fixed until the run starts. The GitHub CLI equivalent is `gh workflow run mousesupremacy-dev-apk.yml --repo xsexiestbeastalivex-rgb/pokedaisy-mousesupremacy --ref "$build_ref"`. Select the resulting successful run by workflow and head SHA, then download the artifact named `pokedaisy-dev-apk-<full-sha>` from that run. [GitHub dispatch documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)

Check the run SHA, artifact name the `Source` commit in the bundled `build-info.txt`, and `assets/source-commit.txt` inside the APK against the intended SHA. A mismatch means the artifact cannot verify the intended source. Verify the ZIP against the Actions digest when available, then verify the APK against `SHA256SUMS`, inspect the package and native ABIs with Build Tools, and verify its signing certificate with `apksigner verify --print-certs`. Record run, artifact, exact SHA, package, ABIs, both digests when available, and signer in the evidence ledger. Preserve the provenance and notices. The archive expires after seven days. When it expires, retain the recorded evidence and rebuild from the reviewed SHA only when the use case requires fresh bytes.

Phase 1 must exercise this procedure on the first packaging-relevant change and verify the downloadable artifact's bundled source SHA. The existing job uses pinned submodules and read-only repository permissions. It requires no retained signing, Firebase or upstream credentials.

## Phase 1C application pointer checkout

Use the exact-commit **MouseSupremacy development APK** with `com.pokedaisy.app.dev`, a verified x86_64 library on the WSA target, and the [ROM-free dev library bootstrap](TESTING.md#rom-free-launch-and-evidence). Complete the [pre-launch save-isolation gate](#pre-launch-save-isolation-gate) before opening a ROM. Use only a disposable device or approved disposable dev install. A signer conflict requires a clean disposable target.

1. Verify the archive against the Actions digest and its `build-info.txt` source, package and signer against the downloaded APK. Check `SHA256SUMS` and both native ABI entries. Start the empty dev library and confirm it appears. Keep the official app and data outside this procedure.
2. After the save gate passes, select the verified disposable copy from the dev library. To opt in before entering the game, choose exactly one marker in the dev app's private `files` directory. Use `ms_pointer_wsa` for the qualified WSA translation, `ms_pointer_android` for conventional mouse only, or `ms_pointer_touch` for enhanced direct-contact observation plus conventional mouse. Existing upstream dispatch stays active in all profiles.

   ```powershell
   # $pdaAdb, $pdaTarget and $pdaPackage come from the ROM-free bootstrap.
   & $pdaAdb -s $pdaTarget shell run-as $pdaPackage mkdir -p files
   & $pdaAdb -s $pdaTarget shell run-as $pdaPackage touch files/ms_pointer_wsa
   # Enter the already verified disposable game from the dev library.
   $pdaPid = (& $pdaAdb -s $pdaTarget shell pidof $pdaPackage | Out-String).Trim()
   if ($pdaPid -notmatch '^\d+$') { throw 'Dev process unavailable' }
   & $pdaAdb -s $pdaTarget logcat -d --pid=$pdaPid -s MsPointer:I
   ```

3. In the disposable game, start with ORIGINAL fit or STRETCH, a docked companion and no over-game HUD or virtual controls for calibration. Hover before pressing. In each of two companion widths, sample the visible top-left, bottom-right and adjacent letterbox or clipping boundary. Capture aligned screenshots if opted in. Expect native GBA coordinates only inside the eligible 240×160 picture. Press and release on the game and companion separately. Try crossing into chrome, resizing or changing focus during a press, then do a fresh press. Repeat with a HUD, dismissible companion overlay or touch controls visible. Confirm the upstream surface responds normally.
4. Record `activity`, `view`, `layout`, `normalized` and `invalidate` records with the marked physical host action and visible result. `view ... activity=false` or `channel=native-pad` helps identify delivery outside the Activity dispatcher. Keep device identifiers and full logs private. Draw IDs represent the GL quad submitted to the surface, so use an aligned image for compositor-level proof. A trace alone provides no native cursor-latency or applied-input measurement. There is no MouseSupremacy key producer in this build.
5. Capture lasts at most 90 seconds or 768 records per game Activity, with coalesced motion. Close the disposable game to leave the trace session and remove the marker with `adb -s <target> shell run-as com.pokedaisy.app.dev rm files/ms_pointer_wsa`. Stop with the specific failed prerequisite if the package, isolation, layout or host cannot be verified. The [FireRed experiment](test-scenarios/firered-battle.md#phase-1-feasibility-experiment) requires exact ROM identity, ready-state and applied-frame evidence beyond this checkout.

### Pre-launch save isolation gate

Use this gate for any GBA, GB/GBC or DS ROM in a dev experiment. The standalone ROM-free pointer probe needs no ROM or save storage. Package verification and installation alone do not clear the save gate.

1. Start in a clean disposable instance or a known disposable dev install. Keep an original-side backup outside any test read/write roots. Copy the exact ROM and any fixture save into dedicated test storage that the official app and other emulators do not use. Prefer one raw ROM file for the first test. Verify the dev library's long-press **INFO → ROM → FOLDER** points to the copy actually selected. Do not use an original frontend shortcut or a file picker entry you cannot trace to that copy.
2. In the dev app, link only the dedicated test ROM directory if a linked folder is needed. Under **Settings → Folders**, set **GAME SAVES** to **DEFAULT**, empty **ALSO LOOK IN**, and verify **SAVE BACKUPS** uses its default sibling directory or only disposable storage. The dev test entry must have no per-ROM **SAVE FOLDER** override. A visible **DEFAULT SAVE FOLDER** action indicates an override. Use a fresh disposable setup if clearing unknown settings could copy files. The per-ROM folder change in the library can copy a currently selected save during the change. Keep dev states and any backups in the same isolated test scope. [Folder settings](../../app/src/main/kotlin/com/pokedaisy/app/SettingsActivity.kt#L1942) · [per-ROM folder change](../../app/src/main/kotlin/com/pokedaisy/app/LibraryActivity.kt#L2186)
3. Without opening the game, long-press the exact dev ROM and open **INFO → SAVE FILE**. Record the absolute **FILE** for an existing save or **WILL BE** for a new one. This uses the same `SavesLocation.saveFor` resolver as game start. Privately resolve both the selected ROM and save destination on the actual target, accounting for filesystem aliases and links. For a new save, resolve the existing parent and check the final basename separately. Resolve the backup destination as well. The default is `<save-parent>/pokedaisy-backups`. Check containment in the approved test paths by path components, including the backup directory if it already exists or its nearest existing parent if it does not. [Backup path](../../app/src/main/kotlin/com/pokedaisy/app/SaveBackups.kt#L45) The GBA/GB default is the dev app's own `files/saves` under its external-files directory. A DS save may instead be next to the **test** ROM, so verify that directory too. If the setting, displayed path, physical directory, backup destination or ROM binding is ambiguous or reaches any original/shared location, stop before launching or editing. Use a disposable Android instance or stay at the ROM-free probe. [INFO save path](../../app/src/main/kotlin/com/pokedaisy/app/GameInfo.kt#L111) · [game start](../../app/src/main/kotlin/com/pokedaisy/app/PokeDaisyActivity.kt#L3520)
4. After the destination passes, place a disposable fixture copy there or use **LOAD SAVE** on the verified dev entry for an appropriate GBA battery save. Use only the agreed test root and re-open **INFO** before play to confirm the resolved file. Recheck before each linked-ROM session and after a package/upgrade, ROM entry, archive name, settings, or storage change. Treat restore, save editor, or state import as separate write operations requiring the same gate. If a fixture update fails, recover from its isolated copy. Keep backups and write evidence outside Git.

The resolver gives a per-ROM override first priority even when empty. Otherwise GBA/GB searches the current global save directory then each extra directory for an existing save. DS puts its ROM directory first if it is writable or already has a matching save. The first searched directory with a matching file wins. If none has a match, a new save goes in the first search directory. The resolver checks each candidate stem in order, preferring an existing `.sav` to `.srm` for that stem. For an archive, its ROM entry stem can precede the archive filename. A copied ROM and apparently empty dev saves folder can still resolve an existing shared save. [Resolver](../../app/src/main/kotlin/com/pokedaisy/app/SavesLocation.kt#L14) · [archive name resolution](../../app/src/main/kotlin/com/pokedaisy/app/RomArchive.kt#L137) · [state root](../../app/src/main/kotlin/com/pokedaisy/app/PokeDaisyActivity.kt#L2655) · [copy/load procedure](../manual/saves.md#load-a-save-file)

**Phase 1 device evidence before linked-ROM testing.** On a disposable Android target, record the revision, device alias and redacted actual ROM, save and backup paths. Keep a separate disposable original-side sentinel with the same save stem and an expected checksum. In the positive case, trigger an ordinary save/write on the verified dev fixture, close it cleanly and verify the copied save changes as expected while the original-side sentinel checksum is identical. For the negative case, deliberately direct a test-only GBA **ALSO LOOK IN** selection at a second throwaway directory representing shared storage and put a matching save there while the dev root lacks one. **INFO** must resolve the sentinel outside the test write root, and the operator must stop before launch or import. If claiming DS coverage, also test a copied DS ROM and a disposable out-of-scope sidecar detected by **INFO**. Recheck the sentinel, restore the clean dev configuration, and record pass, rejection or skip reason with redacted path aliases. The negative case uses throwaway files and never launches the shared-root scenario.

### Retained installations and distribution

Before any retained development install or regular distribution, have the owner approve the distinct package and display identity, signing custody, increasing `versionCode` and human-readable version (including upstream baseline and exact fork build SHA), access policy, and a disabled or fork-only updater. Keep retained signing credentials in a trusted workflow separate from PR-controlled code. Never commit keys or secrets. Test same-package, same-signer in-place upgrade with a higher supported versionCode on disposable fixtures, preserving settings, states and saves. Test that a mismatched certificate is rejected and leaves the installed fixture intact without uninstalling.

Before distribution, audit exported activities, intent links including `pokedaisy://coop`, provider authorities including `${applicationId}.updates`, package-sensitive JNI and scripts, package data roots, import/export, updater host and release settings. Verify the production manifest and APK omit any diagnostic control surface. Preserve credits, [NOTICE](../../NOTICE), [LICENSE](../../LICENSE) and bundled third-party notices. Verify the corresponding exact source, build instructions and pinned submodule/build inputs remain obtainable. Record the verification and owner approval before retained or public distribution.

## Fork maintenance

Maintain the owner's personal PokeDaisy fork as a complete product. Prioritize approved functionality, usability and maintainability. Compatibility with future upstream updates is a high priority. Keep MouseSupremacy modular, reuse upstream functionality where practical, and limit coupling to unstable upstream internals. Retain Android-native input APIs, WSA-first runtime verification and isolated platform adapters. [Architecture](ARCHITECTURE.md)

Preserve upstream Git history and use the controlled sync procedure below. For a sync, pin the previous fork baseline and incoming upstream revision, review the changed seams and gitlinks, and run automated upstream and MouseSupremacy regressions. Include mode-off and existing input behavior where affected, plus the approved fork capabilities touched by the incoming changes. Use exact source and build evidence to localize failures before accepting the sync.

Consider upstream contribution separately when useful and practical. Keep it optional. Choose functionality and engineering effort for the owner's fork based on its requirements, usability, compatibility and maintenance costs. Any upstream communication or submission requires the owner's authorization.

## Git and reviews

Use fork `main` as the reviewed stable branch and a read-only `upstream` remote. Track the upstream tag, commit and any relevant gitlink changes in project status. For sync, start an isolated fork integration branch from current `main`, fetch the new upstream tag and commit, review its changes, merge upstream into the sync branch with history intact and resolve conflicts in focused commits. Run baseline and applicable MouseSupremacy tests, review regressions, then request approval through a fork PR. Preserve dated upstream provenance and both sides of relevant refactor decisions. Avoid force-push and never send branches or PRs upstream without approval.

Use a draft fork PR for substantial work. Include scope, system/requirement IDs, summary, compatibility and architecture effects, exact tests and skipped cases, visual and performance evidence where relevant, known limitations, rollback and independent review outcomes. ## Engineering lifecycle

Apply this workflow to substantial assignments. For a narrow, low-risk change, use the relevant steps and keep the evidence proportional.

1. Review the specifications and scope. Identify the requirement, baseline and measurable acceptance criteria before implementation.
2. Map the affected architecture. For complex stateful work, identify authority, identities, invariants, transitions, lifecycle boundaries, ambiguity and failures.
3. Plan verification before coding. Pin the baseline, reproduce known defects where feasible, choose discriminating methods, and identify proof that needs hardware or the actual application. [Risk-based verification](TESTING.md#risk-based-verification)
4. Implement the root-cause correction and preserve upstream behavior and compatibility outside the approved change.
5. Run focused tests while coding and applicable upstream quick checks at handover. Exercise negative cases and preserve reproducible failing inputs. Use hosted integration and merge checks as applicable. Obtain owner approval for full local suites.
6. Have a separate internal reviewer where available try to disprove the design and test oracle. Give them the invariants, pinned source and ability to run their own checks. With no separate reviewer, run a structured adversarial self-review from a fresh checkout or separately constructed oracle and disclose the limitation.
7. Resolve material findings autonomously. Repeat relevant tests and adversarial review after material corrections, and audit adjacent failures until the [pre-submission gate](../../.agents/skills/verify-mousesupremacy/SKILL.md) is satisfied.
8. Hand over the exact implementation SHA, evidence, and remaining gates for independent acceptance. Independent acceptance can proceed with external checks explicitly pending. Advance non-conflicting work while checks run. Avoid redundant builds and diagnose the evidenced cause before retrying a failed or cancelled job.
9. Obtain scoped physical/runtime proof where acceptance requires it. Platform discovery needed to define requirements can occur earlier. Otherwise, finish automated and internal checks before asking the owner for runtime help.
10. Record the independent verdict and applicable physical proof separately. Before merge, applicable required checks must pass unless the owner authorizes a documented exception. Merge requires owner approval.
11. Update persistent status, requirements, decisions and evidence. Record lessons that change future practice.

Prioritize approved gameplay functionality and reuse established diagnostic and build tooling. The implementation agent owns design, test execution, routine debugging, corrections and evidence. The internal reviewer challenges the weakest claims and test oracle. The independent reviewer issues the acceptance verdict. The owner decides material scope or product direction changes, grants privileged access and approves merge or release. Escalate a genuine blocker the agent cannot resolve, such as inaccessible required hardware or a scope decision. Include the narrow decision or evidence needed and continue unaffected work.

### Repeated-defect escalation

At the second material defect in the same underlying subsystem or failure category, stop isolated symptom-specific patches. Identify the shared cause, reassess the architecture, and audit the whole affected class. Define or strengthen invariants and state transitions, add systematic regression coverage, and show how the correction prevents the class. Rerun applicable regressions and adversarial review. Record the trigger, root cause, design change, tests and limits in the project evidence. Phase 1B input ownership is the recorded example. [Engineering decision](DECISIONS_AND_RISKS.md)

## Agent handoff

| Responsibility | Prerequisite and workflow | Evidence to hand off |
| --- | --- | --- |
| Architecture and engine investigation | Read the approved requirement and source on the pinned baseline. Follow upstream ROM mapping and reader guidance for native state. | File/symbol anchors, confirmed seams, contradicted assumptions and a minimal proof question. |
| Implementation | Link the requirement and design decision, bound the requested behavior, then exercise focused positive and negative cases. | Exact diff and build, commands, test counts, and explicit unverified claims. |
| Gameplay and UX playtesting | Prove the target/package and [isolated save path](#pre-launch-save-isolation-gate). Use the [safe bootstrap](TESTING.md#phase-1-safe-bootstrap) and applicable scenario. | Scoped trace, applied input and native result, presented frame or opt-in capture, with host/input provenance. |
| Compatibility and regression | Record loaded ROM fingerprint/core and per-capability support. Use an exact positive reference and a mismatched fixture or changed context. Compare Mouse Mode off with upstream. | Positive/rejection evidence, lifecycle and input protection checks, and unsupported branches with reasons. |
| Performance | Use matched source, host, ROM, settings and presentation layouts. Repeat controlled input and actual viewport changes. | Sample counts, p50/p95/p99, frame pacing and measured overhead against baseline. |
| Release engineering | Acquire an exact-commit artifact and apply package, signer, source, license and privacy verification. | Reusable run/artifact IDs and checksums, plus applicable distribution or device-gate evidence. |
| Internal adversarial review | Try to falsify invariants and probe uncovered transitions. Use independently designed cases or deliberate mutations. | Findings, reproduction, implementation response and re-verification. Record reviewer availability. |
| Independent review | Start with the requirement, commit and reproduction record as a fresh reader. Reproduce at the smallest feasible layer. | Claim-by-claim verdict, evidence links, gaps, and approved deferrals before merge. |

An agent may cover multiple engineering roles. Keep the implementation, adversarial review and acceptance evidence distinguishable. Start from the documented bootstrap and verify that another reader can reproduce the claim and its negative case without touching the official package. Record the SHA, requirement, prerequisites, commands, evidence grade, gaps and next decision in the PR or project status.
