## Mandatory sequence

1. Define one small playable increment, its exact ROM/host, acceptance limits, preserved upstream behavior, and stop conditions. Separate basic positive flow from broad compatibility and polish. Never mark a wider matrix passed based on the core flow. Emerald and owner-used hacks remain the product priority; retain shared FireRed reference evidence.
2. Reproduce the weakest claim using real application seams early. Plan a minimal frontend smoke run and a negative competing-input case. For lifecycle bugs exercise actual source ownership through final core key write and observed effect, not only a fake scheduler. Reuse existing fixtures, traces, exact builds and platform evidence.
3. Implement in a focused branch or isolated checkout. Run fast focused tests/compile and an internal adversarial pass. Fix blocking defects autonomously. Use bounded recorded histories and failure-class tests. Avoid adding infrastructure unless needed to falsify a material claim.
4. Freeze a candidate source SHA and obtain independent source review **before** expensive distribution/acceptance packaging whenever practicable. Review can overlap focused testing or an explicitly justified early exploratory build. Source acceptance is conditional on remaining hosted and runtime gates. If code changes after acceptance, review the delta and affected claims. Do not build on every review finding.
5. Produce one exact-source acceptance APK after source review and focused tests, plus applicable hosted CI. Use the retained dev signer and payload verifier for CI derivations; verify the actual installed bytes and data isolation. No new signer, migration or full platform checkout absent an evidenced change. Earlier exploratory builds are clearly labelled and never substituted for accepted artifacts.
6. Verify the smallest real playable flow early on an isolated dev target, then expand the agreed matrix. For changes requiring an early frontend experiment, use a locally built disposable dev APK with pinned source/identity, safe save roots and existing owner authorization; never treat an experimental pass as independent acceptance. Consolidate physical owner interactions and automate staging, scenario setup and evidence collection. No owner involvement for work the agents can actually execute.
7. Record exact source, commands, results, skipped checks and limitations. Final merge still requires independent acceptance, applicable CI and scoped physical evidence or explicit owner-approved exception, plus owner merge approval. Keep documentation and source-only changes distinguishable; source-equivalent evidence is reused only when justified and branch rules permit.

## Scope and escalation

Classify discovered issues: (a) regression or blocker to this slice: fix; (b) inherited issue that blocks this slice: minimally correct or safely isolate; (c) unrelated upstream defect: record and defer; (d) architecture improvement or future capability: backlog unless explicitly approved. Repeated-defect escalation is confined to the affected failure class, not a license to redesign adjacent subsystems. If a second material defect, second failed build for the same class, or ~30 minutes of repeated feedback-loop churn occurs, stop blind retries, identify the slowest dependency and cheapest discriminating test, report a concrete recovery plan; continue unaffected work. The 30-minute trigger is a checkpoint, not a deadline or relaxation of safety. Do not repeatedly rerun identical hosted checks without a changed cause. Do not interrupt an already progressing necessary job merely to meet the checkpoint.

## Local incremental build qualification (required before next major gameplay increment)

Owner-approved objective: reusable local Android build lane. Assign the existing local engineering session to qualify it on Windows 11 or existing suitable Linux environment on the owner's machine; prefer reuse of existing JDK/SDK/NDK/Gradle caches and submodules. Inspect actual available tools, disk/RAM and pinned upstream build requirements first. Do not change WSA, official app, user data, system security or release credentials. Use a dedicated checkout outside any active implementation worktree. Use pinned Gradle wrapper, JDK, SDK, NDK, CMake and native submodules from the exact candidate source; skip optional dependencies only as upstream supports. Test focused Android and shared unit commands, one dev x86_64 build (or existing supported ABI configuration), and a second no-change/incremental build. Measure cold and warm wall-clock durations, task reuse and failures; record versions, exact commands and cache paths without private identifiers. Do not alter tracked source simply to manufacture a timing. A harmless isolated test-source change can measure recompilation and be reverted locally. Verify dev package, ABI, source stamp or explicit local provenance and signer before any future device use. Do not publish local private fixtures or keys; no installation needed to qualify build performance. Reuse authorized signing procedure or report how local debug artifacts will be made compatible, without generating a replacement key.

Completion: reproducible commands, successful focused actual Android tests and verified dev APK, measured incremental timing, documented limits and a handoff that another session can execute. If blocked, show exact cause and alternative (e.g. persistent Linux checkout, focused hosted test-only job) rather than merely repeating CI. No blanket permission for full local suites; obtain owner approval when required. No workflow YAML or branch-protection changes without a bounded proposal and review. GitHub Actions remains authoritative hosted regression and artifact provenance, not the sole edit-test loop. Until qualified, use focused checks and source-first review; do not falsely claim the local lane exists.

## Operating responsibilities

Headquarters owns priority, scope and acceptance gates. Implementation owns reproducible focused testing and routine corrections. Independent reviewer challenges source and test oracle before expensive packaging; artifact verification follows build. Local session owns incremental build qualification, repeatable fixtures and scoped actual-runtime checkout. Preserve all earlier approvals and documented limitations. No new conversation is required merely to record a routine correction. Maintain PR evidence and project status; use a separate docs-only change for policy so an active gameplay source SHA is not invalidated.
