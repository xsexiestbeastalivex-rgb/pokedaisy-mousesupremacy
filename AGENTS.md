# PokeDaisy MouseSupremacy

Start with [project status](docs/mousesupremacy/PROJECT_STATUS.md), [requirements](docs/mousesupremacy/REQUIREMENTS.md) and the applicable [system specification](docs/mousesupremacy/specifications/README.md). Read [upstream instructions](CLAUDE.md) for repository conventions, [development notes](docs/DEVELOPMENT.md) for code and tooling, and [ROM capabilities](docs/ROM_FEATURES.md) for changes affecting support. Reuse the [upstream ROM investigation playbooks](.claude/skills/add-rom/SKILL.md) when identifying or extending a ROM.

- The primary objective is the owner's fully functional, independently maintained personal PokeDaisy fork. Prioritize approved functionality, usability and maintainability. Treat upstream contribution as optional. Use modular changes, upstream reuse, controlled synchronization and automated compatibility regressions to keep updates practical. [Fork maintenance](docs/mousesupremacy/DEVELOPMENT.md#fork-maintenance)
- Work inside this fork on focused branches. Preserve upstream history, attribution, settings, saves and keyboard/controller behavior. Keep feature and baseline changes separable. Merge substantial changes or publish releases only with the project owner's approval.
- Begin with the governing specification, requirement ID, approved scope and reproducible acceptance criteria. Pin the baseline, platform, ROM or fixture and evidence grade. For complex stateful work, define invariants, state transitions and failure modes before implementation.
- Let the game decide gameplay. Observe read-only state and use normal emulator inputs for MouseSupremacy. Unrecognized, transitioning or stale contexts must produce zero gameplay input. Preserve companion, HUD, zoom, expansion and DS touch.
- Use [standard Android input APIs](docs/mousesupremacy/ARCHITECTURE.md#android-native-input-and-wsa-first-verification) as the baseline. Verify first on the owner's WSA installation and isolate WSA translation in its adapter. Keep shared interaction logic host-neutral and reuse PokeDaisy touchscreen, keyboard, controller and emulator-input paths. Add emulator-specific adapters only for demonstrated differences. Scope compatibility claims to tested targets and keep the stock Android verification prerequisites for broader production support.
- Reuse upstream readers, geometry and frame scheduling. Run focused tests while coding and upstream quick checks at handover where applicable. Full local suites require owner approval. Capture real runtime evidence for behavior claims and label source findings, fixtures, mocks, headless runs, Android frontend runs and WSA physical tests separately.
- Keep ROMs, BIOS files, saves, private traces and secrets out of commits, artifacts and public discussions. Use the [safe test bootstrap](docs/mousesupremacy/TESTING.md#phase-1-safe-bootstrap) and [verify the resolved save destination](docs/mousesupremacy/DEVELOPMENT.md#pre-launch-save-isolation-gate) before opening or editing a ROM's save. Review diagnostic bundles before sharing them.
- Fix the defect class and audit related behavior. A second material defect in the same subsystem or failure category requires the [repeated-defect escalation](docs/mousesupremacy/DEVELOPMENT.md#repeated-defect-escalation). Select [risk-based tests](docs/mousesupremacy/TESTING.md#risk-based-verification) that challenge expected, unexpected and conflicting behavior. Use systematic histories for ordering and ownership, and verify representative test effectiveness with mutations where practical.
- For substantial work, use a separate internal adversarial reviewer where available. Resolve material findings autonomously, then repeat relevant tests and review. If a separate reviewer is unavailable, perform a structured adversarial self-review and disclose that limitation. Keep internal review, independent acceptance and owner approval distinct.
- Prioritize approved gameplay over speculative infrastructure. Implement, review, correct and retest in one assignment. Use authorized tools directly and involve the owner only for genuine decisions or unavailable access or hardware.
- Independent acceptance may proceed with external checks explicitly pending. Record physical proof separately. Applicable required checks must pass before merge unless the owner authorizes a documented exception. Diagnose failed or cancelled jobs before retrying. Reuse source-equivalent build evidence when the branch rules allow.
- Complete the [pre-submission gate](.agents/skills/verify-mousesupremacy/SKILL.md) before requesting independent acceptance. Record exact source and build, evidence level, limitations and next milestone in the project documents. Report only verification that ran. Use the [engineering lifecycle](docs/mousesupremacy/DEVELOPMENT.md#engineering-lifecycle) to resolve routine work without involving the owner.

The [project index](docs/mousesupremacy/README.md) explains document ownership and the approval workflow.
